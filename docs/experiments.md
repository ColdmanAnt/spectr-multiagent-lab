# План экспериментов

## Дизайн сравнения

Единица эксперимента — смена с заданным seed, горизонтом, способом распределения, настройкой переговоров, защитой и сценарием сбоя. Для парного сравнения сохраняются одинаковые seed и горизонт. На одном seed задаётся один начальный набор исследований.

Базовый факторный план:

| Распределение | Переговоры |
| --- | --- |
| Центральное | Выключены |
| Центральное | Включены |
| Контрактная сеть | Выключены |
| Контрактная сеть | Включены |

Сравнивайте механизмы распределения при фиксированном состоянии переговоров. Эффект переговоров оценивайте внутри одного механизма распределения. Для ЛР4 повторите тот же план с включённой и выключенной защитой. Это помогает не приписать эффект одной настройки другой.

## Запуск

```sh
node experiments.mjs --seeds 20 --scenario normal --horizon 180 --out results/baseline
node experiments.mjs --seeds 20 --scenario all --horizon 180 --compare-protection --out results/reliability
```

Первый запуск даёт 80 прогонов. Во втором для пяти сценариев выполняются четыре сочетания настроек, два состояния защиты и 20 seed — 800 прогонов. Реальное число строк подтверждается файлом `runs.csv`.

Чтобы исследовать только режим без защиты:

```sh
node experiments.mjs --seeds 20 --scenario ghost --no-protection --out results/ghost-unprotected
```

Параметр `--scenario all` включает нормальную работу как контрольную группу. В сценариях сбой вводится движком на заданном такте, поэтому нужен горизонт, достаточный для его появления. Для демонстрации можно вводить сбои вручную; такие прогоны сравнимы, только если тип сбоя и такт ввода совпадают.

## Файлы результатов

- `runs.csv`: конфигурация и метрики каждого отдельного прогона.
- `summary.csv`: среднее (`_mean`) и выборочное стандартное отклонение (`_sd`) каждой числовой метрики по одинаковым настройкам. При одном прогоне отклонение записывается как 0; это не оценка устойчивости.
- `experiment.json`: полные строки, сводка, настройки запуска и отметка времени выгрузки.
- JSON трассы из интерфейса: подробная последовательность конкретной смены; используется для объяснения механизма и сбоя.

Одинаковые настройки воспроизводят строки результатов. Время создания JSON — метаданные выгрузки и может отличаться. CSV использует запятую как разделитель и UTF-8 с BOM; при импорте в таблицы явно выберите разделитель и типы столбцов.

## Что измерять

Поля метрик возвращает `getState().metrics`. Точные определения соответствуют вычислениям в `dist/engine.js`, а не времени работы браузера.

| Поле | Что показывает |
| --- | --- |
| `completed` | Завершения, принятые моделируемой системой |
| `validCompleted` | Действительно корректные завершения по состоянию среды |
| `late` | Завершения после срока, учитываемые движком |
| `utility` | Ценность корректных результатов (35% при опоздании) минус 0,18 за такт ожидания; переводы кредитов в сумме сокращаются |
| `messages` | Число сообщений протоколов |
| `meanWait` | Среднее от появления до последнего старта по всем запускавшимся задачам, включая задержку до повтора |
| `utilization` | Занятые такты установок / (3 × прошедшее время); простой offline входит в знаменатель |
| `fairness` | Индекс Джейна по долям выполненных задач научных групп; 0–1 |
| `recoveries` | Зафиксированные восстановительные действия |
| `violations` | Нарушения, учитываемые моделью |
| `undetected` | Принятые недостоверные результаты плюс принятые повторные сообщения |

Не объединяйте `completed` и `validCompleted`: без проверки ложная отчётность может создать видимость высокой производительности. Число восстановлений само по себе не является оценкой качества — оно может расти из-за большего числа обнаруженных проблем.

Индекс Джейна для долей выполненных планов `x_i` вычисляется как `(Σx_i)² / (n·Σx_i²)`. Он показывает равномерность, но не достаточность результата: одинаково низкое выполнение всех планов тоже может быть равномерным. Рассматривайте его вместе с полезностью и числом корректных завершений. Случай отсутствия выполненных задач трактуется движком отдельно.

## Время до результата для ЛР2

```sh
node tools/measure_completion.mjs
```

`results/coordination-times.json` содержит 40 повторных штатных смен: seed 1–20 для диспетчера и контрактной сети, переговоры выключены, защита включена, горизонт 180 тактов. В каждом прогоне считается среднее `finishedTick - release` по уникальным достоверно завершённым исследованиям; сводка содержит среднее и выборочное SD этих значений по 20 прогонам.

Незавершённые заявки исключены из этого условного среднего и подсчитаны отдельно в `unfinished`. Механизмы завершают разные подмножества задач, поэтому временную метрику следует читать вместе с числом завершений. Она дополняет `meanWait`, которое измеряет время только до последнего старта.

## Гипотезы для проверки

1. Контрактная сеть может потребовать больше сообщений, одновременно по-другому учитывая локальную загрузку.
2. Переговоры могут уменьшить опоздания ценных задач, но ухудшить равномерность выполнения планов.
3. Проверка сообщений может снизить число ошибочно принятых результатов ценой дополнительной работы.
4. Срок действия резервирования может уменьшить потери от фиктивной брони.

Это гипотезы, а не заранее установленные результаты. Если различия малы или направление противоположно ожидаемому, следует объяснить их трассами, нагрузкой и правилами модели.

## Анализ

Для каждой пары настроек посчитайте разность показателей на каждом seed, затем среднюю парную разность и её разброс. Отдельно рассматривайте нормальную работу и каждый тип сбоя. Полезны графики «полезность — число сообщений», доля корректных результатов, выполнение планов по группам и временная шкала одного характерного сбоя.

Сначала проверьте, возник ли исследуемый конфликт: есть ли очереди, дефицит и сообщения переговоров. Если задачи успевают без конкуренции, отсутствие эффекта переговоров ожидаемо. Увеличение горизонта может сгладить различия, поскольку позднее завершаются почти все задачи.

Не переносите выводы на реальные ядерные лаборатории. В отчёте укажите версию исходников, настройки, список seed, формулы, число прогонов и ограничения модели. Отдельно сообщайте функциональные тесты и результаты экспериментов: прохождение тестов не доказывает превосходства алгоритма.
